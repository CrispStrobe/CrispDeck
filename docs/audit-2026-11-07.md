# CrispDeck security and reliability audit — 2026-11-07

## Scope and status

This review identified and fixed credential disclosure paths, missing feed ownership checks, unsafe server-side URL fetching, publishing races, native storage weaknesses, and release workflow input handling. The changes have regression coverage and were saved through incremental commits and pushes to the feature branch. This report records the work and its limits; it is not a claim that the application is free of vulnerabilities.

- Source base: [`c01c588f744ca3603643f03ccad6be73a2af7a2b`](https://github.com/CrispStrobe/CrispDeck/commit/c01c588f744ca3603643f03ccad6be73a2af7a2b).
- Branch: [`fix/audit-security-reliability-2026-11-07`](https://github.com/CrispStrobe/CrispDeck/tree/fix/audit-security-reliability-2026-11-07).
- Review: [pull request #84](https://github.com/CrispStrobe/CrispDeck/pull/84).
- CI status at this reporting checkpoint: checks for the latest pushed commit were pending or queued. Local results below do not establish a successful remote CI run.

The review covered browser credentials, account selection, OAuth boundaries, exports and diagnostics, the service worker, draft scheduling, feed and Threads server endpoints, native database migrations, Tauri capabilities, and Apple release workflows. Tests used synthetic accounts and mocked service boundaries. No live social account was authenticated, no post was published, and no production subscription records were deleted during validation.

A bounded secret/log review of 277 tracked application, API, native, release, and configuration source files found no confirmed committed private keys, provider credential literals, or additional direct token logging. Tests, generated content, repository history, and live deployment secrets were outside that scan. This is not a historical secret audit.

## Confirmed issues and changes

### 1. Saved Bluesky credentials are bound to the account's DID

The client previously accepted inadequately checked PDS metadata and could resolve a saved account through a mutable handle. A reassigned handle could therefore send the old account's saved app password to a different account's PDS.

[`src/lib/api/bluesky.ts`](../src/lib/api/bluesky.ts) now validates supported DID forms, requires a matching DID document identity, and checks both the PDS service identifier and service type. Credential destinations must be HTTPS origins without embedded credentials, paths, queries, or fragments. [`client-factory.ts`](../src/lib/api/client-factory.ts) selects saved accounts by immutable DID and verifies that the authenticated session returns that DID. Legacy saved app-password accounts without a DID require reconnection.

DID-based password login also fails before the SDK login call when discovery fails or metadata is unsafe. It does not send the saved secret to the default server. Initial handle-based sign-in retains its existing default-server fallback. Tests cover reassigned handles, mismatched sessions, malformed documents, unsafe destinations, failed discovery, and a successful retry without caching a fallback destination: [`bluesky.pds.unit.test.ts`](../src/lib/api/bluesky.pds.unit.test.ts) and [`client-factory.identity.test.ts`](../src/lib/api/client-factory.identity.test.ts).

### 2. Backups, credential persistence, diagnostics, and CSV exports

Settings backups could include the actual browser encryption seed and salt, provider API keys, and registration secrets. Imports could overwrite device key material or attach an existing API key to an imported endpoint. [`src/lib/settings-export.ts`](../src/lib/settings-export.ts) excludes credential and encryption keys and uses an allowlist for provider preferences. Import applies the same filtering, requires provider secrets to be entered again, and reports storage failures. [`settings-export.test.ts`](../src/lib/settings-export.test.ts) covers old backups, malformed configurations, and endpoint/key separation.

[`browser-db.ts`](../src/lib/browser-db.ts) now refuses credential writes if the encryption seed or salt cannot be persisted, preventing an apparently successful account connection whose credentials become unreadable after reload. [`browser-credentials.test.ts`](../src/lib/browser-credentials.test.ts) verifies failure handling and decryption after a module reload.

[`debug-log.ts`](../src/lib/debug-log.ts) redacts bearer tokens, OAuth query parameters, password/API-key fields, and Bluesky access/refresh JWT fields before truncation or diagnostic export. Circular objects, big integers, and unserializable values no longer make logging throw. [`utils/export.ts`](../src/lib/utils/export.ts) escapes every CSV column and neutralizes spreadsheet formulas in remote text, handles, and URLs. Focused privacy and CSV regressions accompany both changes. These protections do not retroactively remove secrets from backups or diagnostic files already shared.

### 3. Feed mutation now authenticates ownership

Feed publishing and deletion previously trusted a caller-supplied DID and record key. Shared record-key storage and cache entries could also mix definitions belonging to different accounts.

[`api/_lib/feed-auth.ts`](../api/_lib/feed-auth.ts) now verifies short-lived PDS-signed service JWTs, including issuer, service audience, intended action, time bounds, key identity/controller, and cryptographic signature. It uses the official AT Protocol crypto and identity packages, retaining the resolver's private-network protections. Account access and refresh tokens are not accepted as service tokens. This follows [AT Protocol inter-service authentication](https://atproto.com/specs/xrpc#inter-service-authentication).

[`api/feed/publish.ts`](../api/feed/publish.ts), [`unpublish.ts`](../api/feed/unpublish.ts), and [`api/_lib/feed-storage.ts`](../api/_lib/feed-storage.ts) use owner-qualified object paths, bounded JSON parsing, and validated keys. Legacy definitions remain readable only when their stored owner matches. [`getFeedSkeleton.ts`](../api/xrpc/app.bsky.feed.getFeedSkeleton.ts) includes the full account identity in cache keys. [`src/lib/feed-builder.ts`](../src/lib/feed-builder.ts) obtains action-scoped service tokens and preserves definitions after uncertain publishing failures; rollback is limited to definite rejection, avoiding deletion of a query that a published feed may already reference.

[`feed-api.test.ts`](../src/lib/feed-api.test.ts) and [`feed-builder.test.ts`](../src/lib/feed-builder.test.ts) exercise forged and expired tokens, real signature verification, mismatched owners, private DID destinations, bounded bodies, same-key account isolation, legacy ownership, and uncertain publication outcomes.

### 4. Unfinished background push stops collecting secrets

The background push backend was unfinished but accepted subscription endpoints and authentication material into public Blob storage and could imply that delivery was active. [`api/push/subscribe.ts`](../api/push/subscribe.ts), [`vapid-key.ts`](../api/push/vapid-key.ts), and [`send.ts`](../api/push/send.ts) now report unavailable functionality with HTTP 501 instead of collecting new secrets or pretending to deliver notifications. Missing cron credentials cannot authenticate a request.

The [settings page](../src/routes/settings/+page.svelte) communicates unavailability and can revoke the browser subscription locally before attempting legacy server cleanup. Legacy deletion checks possession of the exact stored subscription rather than trusting a user identifier alone. [`push-api.test.ts`](../src/lib/push-api.test.ts) verifies that no new subscription is persisted, unavailable delivery is reported honestly, and cleanup refuses mismatched proof.

If the old backend was used, operators must assess existing public subscription records, revoke affected subscriptions where appropriate, and remove obsolete records. This code change does not prove that historical public copies disappeared. Background delivery remains intentionally disabled until a complete design with appropriate private storage and authorization is implemented.

### 5. Threads URL fetching, tokens, and native transport

[`api/threads/resolve-repost.ts`](../api/threads/resolve-repost.ts) previously allowed attacker-selected fetch destinations or redirects. It now permits only HTTPS Threads post permalinks on approved hosts, checks every redirect, and applies a deadline. Regression tests reject unsafe hosts, paths, and redirect destinations.

[`api/threads/token.ts`](../api/threads/token.ts) and [`src/lib/api/threads.ts`](../src/lib/api/threads.ts) use the correct `/refresh_access_token` endpoint. The server bounds parsing, limits upstream requests, prevents token-response caching, preserves large user IDs as strings, and keeps a valid short-lived token when an optional upgrade fails. Errors avoid disclosing token values.

Native Threads writes, deletes, token operations, and settings connection checks now use the native HTTP transport consistently with reads. Tests force browser fetch to fail and verify the native boundary across create/poll/publish and authentication operations. They establish transport selection, not successful interaction with a real Threads account. See [`threads-token-api.test.ts`](../src/lib/threads-token-api.test.ts), [`threads-native.test.ts`](../src/lib/api/threads-native.test.ts), and [`threads-repost-api.test.ts`](../src/lib/threads-repost-api.test.ts).

### 6. Draft deletion, stale sends, and scheduling races

The [drafts page](../src/routes/drafts/+page.svelte) and [composer](../src/routes/compose/+page.svelte) now use the established publishing deletion/scheduling helpers, which coordinate locks and cancel queued delivery. A failed discard preserves the editable draft and reports the error.

[`src/lib/publishing/drafts.ts`](../src/lib/publishing/drafts.ts) reloads current persisted content before publishing and rejects a deleted draft instead of recreating delivery from an old UI snapshot. Scheduled delivery rechecks the current due time under the existing draft-write lock, freezes a new job while that lock is held, and skips a tick when an edit owns the lock. Explicit manual sends remain possible; existing queued jobs retain their frozen content, and failed/partial jobs require review. [`drafts.test.ts`](../src/lib/publishing/drafts.test.ts) and [`draft-safety.test.ts`](../src/routes/drafts/draft-safety.test.ts) cover deleted rows, newer edits, rescheduling, busy locks, job cancellation, and manual-send behavior.

### 7. Offline cache and notification boundaries

[`static/sw.js`](../static/sw.js) now derives paths and cache names from its registration scope, compares origins exactly, and avoids deleting another app's caches. It excludes OAuth callbacks, API/XRPC requests, and authorization-bearing requests from interception, respects private/no-store responses, and purges this installation's old cached callback URLs. Notification clicks stay inside the current app scope. Cache failures no longer replace a successful network response, and offline misses produce defined responses. [`service-worker.test.ts`](../src/lib/service-worker.test.ts) covers scope isolation, hostile notification URLs, legacy callback cleanup, cache exhaustion, and offline behavior.

### 8. Native storage, capabilities, OAuth, and release workflows

[`src-tauri/src/db/mod.rs`](../src-tauri/src/db/mod.rs) applies migrations and version records in one transaction, temporarily disables foreign-key enforcement before table rebuilds, checks references before commit, and restores enforcement afterward. This prevents rebuilding `accounts` from cascade-deleting cached follows or nulling identity links. [Migration 006](../src-tauri/migrations/006_identity_link_indexes.sql) restores dropped indexes. Added Rust regressions cover preservation, rollback, invalid references, nested transactions, and indexes; their execution status belongs in the native validation section below. The migration cannot reconstruct rows lost during an earlier upgrade.

Selected system-keychain writes now fail closed instead of silently falling back to local encryption. Explicit local storage and legacy reads remain supported. [`app_data.rs`](../src-tauri/src/app_data.rs) makes the application data directory private to the Unix user with mode 0700 and propagates failures. Local encryption still does not protect secrets from another process running as the same user; its hostname-derived design also has backup/portability limits.

[`tauri.conf.json`](../src-tauri/tauri.conf.json) adds a production content security policy limiting executable scripts to bundled content while preserving IPC, configured network providers, media, and HLS workers. [Native capabilities](../src-tauri/capabilities) remove broad mobile file access and unused arbitrary-path JSON-store access. Export access uses the save dialog and text-file write permission. [`auth_commands.rs`](../src-tauri/src/commands/auth_commands.rs) permits HTTPS sign-in navigation without URL credentials and matches callback URIs exactly apart from query/fragment.

Four [Apple workflows](../.github/workflows) now pass dispatch inputs and signing secrets through environment variables and quoted arguments/arrays. Temporary signing files receive restrictive permissions. [`test_workflow_inputs.py`](../scripts/test_workflow_inputs.py) passes hostile strings through the shell as literal data, and [`test_native_capabilities.py`](../scripts/test_native_capabilities.py) checks permission/CSP constraints. No signing, notarization, App Store upload, or device keychain flow was performed during this review.

## Dependency changes and remaining advisories

[`package.json`](../package.json) and the [lockfile](../package-lock.json) update DOMPurify to 3.4.17, Vite to 6.4.5, Vitest to 4.1.12, and SvelteKit to 2.70.4. Constructor mocks were updated for Vitest 4 and their behavioral assertions retained. SvelteKit 2.70.4 includes a security backport for escaping prerendered cache-control headers; the [vendor advisory's version metadata](https://github.com/sveltejs/kit/security/advisories/GHSA-27mw-82g8-phjj) identifies 2.70.4 as patched, although its prose and npm's affected range had not caught up.

The initial npm audit reported 28 affected package entries (3 critical, 18 high, 1 moderate, 6 low). After compatible updates it reports **22 affected package entries: 16 high and 6 low**, with zero critical or moderate entries. Undici also advances to 6.29.1 and source-map-js to 1.2.2 through the lockfile.

The 16 high entries propagate one [Zod memory-exhaustion advisory, GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), through the AT Protocol dependency tree. These are not 16 independent high-severity defects. The latest official API, browser OAuth, JWK, and identity package paths still require Zod 3; upgrading those SDKs would not remove this finding. The [Zod 3 issue](https://github.com/colinhacks/zod/issues/6653) remains open, and its maintainer says v3 releases have stopped. Forcing Zod 4 would cross incompatible APIs and was not applied. The bounded request readers reduce exposure at the changed endpoints, but do not remove the dependency risk.

The six low package entries reported by npm relate to [SvelteKit form redirects](https://github.com/advisories/GHSA-pfhg-q3qv-9q6r), the already-backported prerender-header fix, [cookie validation](https://github.com/advisories/GHSA-pxg6-pf52-xh8x), and [deepmerge prototype poisoning](https://github.com/advisories/GHSA-gcqx-w48m-w2h4). The current compatible dependency ranges do not resolve the cookie/deepmerge entries. Production-only npm audit retains the 16 high entries. Counts describe the dependency graph and registry data; they do not demonstrate that each advisory is exploitable through CrispDeck.

### Native execution scope

The environment lacks the GTK/WebKit development libraries for the complete Tauri application. A temporary Rust harness compiled the production database, credential-store, credential-encryption, app-data, and URL-validation modules directly from their source paths. It used vendored D-Bus solely to supply missing development headers and the same URL type re-exported by Tauri; it did not compile or instantiate the desktop WebView command. All **88 tests passed**. The run exposed two assumptions in newly added tests: SQLite's default foreign-key setting and an existing temporary-directory parent. The tests now set up those conditions explicitly. This exercises the real migration and credential logic, with fake OS-store tests, but does not establish a full native build or real keychain behavior.

The repository's normal native gates remain `cargo test --lib --locked` and `cargo check --locked` on Linux, macOS, and Windows. The browser gate remains `npx playwright test --reporter=list`. Check their results in PR #84 before release; no native platform pass is inferred from the other results.

```sh

npx tsc --project api/tsconfig.json --noEmit

python3 -m unittest discover -s scripts -p 'test_*.py'

```

The audit commands still exit nonzero for the disclosed residual findings. Package counts and advisory metadata are a dated snapshot, so future runs may differ.

Before deploying, review existing push subscription records and any backups or diagnostic exports made with earlier versions. Re-enter provider keys after a sanitized settings import. Reconnect legacy Bluesky app-password records that have no immutable DID. Retain deployment-level abuse controls for public endpoints: this change adds bounded inputs and short-lived authorization, not a distributed replay store or rate limiter. Existing SQLite data loss cannot be reconstructed by the new migration. Complete the native/browser checks and the [device/account validation matrix](validation.md) with dedicated accounts. This audit made no release, production deployment, credential rotation, or signing change outside the feature branch.
